# x402 Integration

How TEESwap receives payment from users via the x402 protocol.

Spec: https://docs.x402.org
Source: https://github.com/x402-foundation/x402

## Overview

x402 is a payment protocol with two transports:

- **HTTP**: the server answers `402 Payment Required` with payment requirements,
  the client retries with a signed payment in HTTP headers.
- **MCP**: payment travels inside the JSON-RPC messages of a `tools/call`; no
  HTTP status codes or headers are involved. See [MCP transport](#mcp-transport).

TEESwap serves both: its tools are exposed over MCP and REST, and each speaks
its own transport (see [Tools and transports](#tools-and-transports)).

Either way, the client signs a payment authorization, a facilitator settles it
on-chain, and the TEE then has funds to work with. The TEE never has its own
funds. Everything starts with the user paying in.

## MCP transport

Spec: [`specs/transports-v2/mcp.md`](https://github.com/x402-foundation/x402/blob/main/specs/transports-v2/mcp.md)
(x402 v2). TEESwap implements it as written.

### Flow

```
Client                                           Server (TEE)
  │  tools/call  (no payment)                        │
  │ ───────────────────────────────────────────────► │
  │  result: isError: true                           │
  │          structuredContent: PaymentRequired      │
  │          content[0].text:  same, JSON-encoded    │
  │ ◄─────────────────────────────────────────────── │
  │                                                  │
  │  tools/call  (same call)                         │
  │    params._meta["x402/payment"]: PaymentPayload  │
  │ ───────────────────────────────────────────────► │
  │                               verify → execute → settle (facilitator)
  │  result: the tool's content                      │
  │    _meta["x402/payment-response"]: settlement    │
  │ ◄─────────────────────────────────────────────── │
```

Payment-required and settlement failure are **tool results** (`isError: true`),
not JSON-RPC errors.

### 1. Payment required

Servers MUST return a tool result with `isError: true` containing the
`PaymentRequired` data, and MUST provide it in both formats:

- `structuredContent` (REQUIRED): the `PaymentRequired` object
- `content[0].text` (REQUIRED): the same `PaymentRequired`, JSON-encoded

Clients SHOULD prefer `structuredContent` when available, falling back to
parsing `content[0].text`.

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "isError": true,
    "structuredContent": {
      "x402Version": 2,
      "error": "Payment required to access this resource",
      "resource": {
        "url": "mcp://tool/financial_analysis",
        "description": "Advanced financial analysis tool",
        "mimeType": "application/json"
      },
      "accepts": [
        {
          "scheme": "exact",
          "network": "eip155:84532",
          "amount": "10000",
          "asset": "0x036CbD53842c5426634e7929541eC2318f3dCF7e",
          "payTo": "0x209693Bc6afc0C5328bA36FaF03C514EF312287C",
          "maxTimeoutSeconds": 60,
          "extra": { "name": "USDC", "version": "2" }
        }
      ]
    },
    "content": [
      { "type": "text", "text": "{\"x402Version\":2,\"error\":\"Payment required to access this resource\", …}" }
    ]
  }
}
```

### 2. Paying

The client repeats the tool call with the payment at `params._meta["x402/payment"]`:
the `resource`, the chosen entry from `accepts` as `accepted`, and the signed `payload`.

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "financial_analysis",
    "arguments": { "ticker": "AAPL", "analysis_type": "deep" },
    "_meta": {
      "x402/payment": {
        "x402Version": 2,
        "resource": {
          "url": "mcp://tool/financial_analysis",
          "description": "Advanced financial analysis tool",
          "mimeType": "application/json"
        },
        "accepted": {
          "scheme": "exact",
          "network": "eip155:84532",
          "amount": "10000",
          "asset": "0x036CbD53842c5426634e7929541eC2318f3dCF7e",
          "payTo": "0x209693Bc6afc0C5328bA36FaF03C514EF312287C",
          "maxTimeoutSeconds": 60,
          "extra": { "name": "USDC", "version": "2" }
        },
        "payload": {
          "signature": "0x2d6a…571c",
          "authorization": {
            "from": "0x857b06519E91e3A54538791bDbb0E22373e36b66",
            "to": "0x209693Bc6afc0C5328bA36FaF03C514EF312287C",
            "value": "10000",
            "validAfter": "1740672089",
            "validBefore": "1740672154",
            "nonce": "0xf374…3480"
          }
        }
      }
    }
  }
}
```

### 3. Settlement

On success the result is the tool's normal content, with the settlement at
`_meta["x402/payment-response"]`:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [{ "type": "text", "text": "Financial analysis for AAPL: …" }],
    "_meta": {
      "x402/payment-response": {
        "success": true,
        "transaction": "0x1234…cdef",
        "network": "eip155:84532",
        "payer": "0x857b06519E91e3A54538791bDbb0E22373e36b66"
      }
    }
  }
}
```

### Settlement failure

The server returns a tool result with `isError: true` in the same format as
payment required, with `error` describing the failure (e.g. `"Settlement failed"`).
If settlement fails after the tool has already executed, the server does not
return the tool's content, only the payment error.

### TEESwap tools and payment

Every invoice has a deposit address derived inside the TEE. Funding an invoice
means getting its input tokens to that address, either by a deposit the client
makes or by an x402 payment the facilitator settles.

The funding method is chosen **when the invoice is quoted**, because it
constrains what can be quoted: x402 needs a single token input (see
constraints below). The invoice records it, and it can't change afterwards.
Each method has its own tools, so every tool has one input type and one output
type:

| Tool | Input | Output (success) |
|---|---|---|
| `teeswap_quote` | `QuoteRequest` | `QuoteResponse` — invoice funded by deposit |
| `teeswap_quote_x402` | `QuoteRequest` | `QuoteResponse` — invoice funded by x402; x402 constraints checked here |
| `teeswap_accept` | `InvoiceRequest` | deposit instructions |
| `teeswap_accept_x402` | `InvoiceRequest` | invoice ID and status, `_meta["x402/payment-response"]` |
| `teeswap_execute` | `QuoteRequest` | quote + accept in one call, deposit |
| `teeswap_execute_x402` | `QuoteRequest` | quote + accept in one call, x402 |

An accept only takes invoices of its own funding method; the other is a domain
error that names the right tool.

The x402 tools are `PaidTool`s (see [Tools and transports](#tools-and-transports)),
over either interface:

1. **Unpaid call.** Returns `PaymentRequired` with one `accepts` entry for the
   invoice's input: `payTo` = the deposit address, `amount` = the input amount,
   `maxTimeoutSeconds` = the invoice's remaining validity. `resource.url` names
   the invoice.
2. **Paid retry.** The client repeats the same call with the payment. The tool
   finds the invoice from it (`accepted.payTo` is its deposit address), checks
   it against the invoice's terms, and settlement moves the tokens to the
   deposit address (settlement design: open, see below).
3. **Result.** The invoice ID and status, with the settlement result.
   Execution continues in the engine; progress is read with `teeswap_status` /
   `teeswap_invoice`.

The unpaid `PaymentRequired` is the x402 spec's `isError` result, outside the
tool's success output schema, like TEESwap's other tool errors.

Both funding methods end in the same state, input tokens at the deposit
address, so the engine, the invoice and its work log are the same either way.

Constraints on x402 funding:

- **One input token.** An x402 payment settles one `accepts` entry.
- **Tokens only.** x402 schemes move tokens (EIP-3009, Permit2, SPL); native
  ETH can't be paid this way.

### Tools and transports

Every TEESwap tool is exposed twice: over MCP (`tools/call`) and over REST
(`POST /teeswap/<tool>`). Each interface speaks its own x402 transport, so
payment is handled below both of them and the transports only translate.

A tool is either a `Tool` or a `PaidTool`. They share a base (definition,
schemas, routing), and neither overrides the other's `execute`:

```python
class Tool(ToolBase):
    async def execute(self, args: A) -> R

class PaidTool(ToolBase):
    async def execute(self, args: A, payment: Payment | None) -> R | PaymentRequired
```

`PaidTool` isn't a subclass of `Tool`: its `execute` takes a payment and can
return `PaymentRequired`, which a `Tool` never does. Keeping them separate
means each tool's type says exactly what it can do.

The flow:

1. The client calls a paid tool with no payment. `execute` gets
   `payment=None` and returns `PaymentRequired`.
2. The transport renders it: an `isError` result with `structuredContent` and
   `content[0].text` over MCP; `402` with a `PAYMENT-REQUIRED` header over HTTP.
3. The client repeats the call with a payment. The transport hydrates
   `Payment` from `params._meta["x402/payment"]` (MCP) or the
   `PAYMENT-SIGNATURE` header (HTTP) and passes it to `execute`.
4. The tool handles the payment itself: finds what it is for, checks it
   against its terms, and proceeds, or returns `PaymentRequired` again with
   `error` set.
5. **Open:** settlement: how and against which facilitator it happens, and how
   its result reaches the transport as `_meta["x402/payment-response"]` (MCP)
   or the `PAYMENT-RESPONSE` header (HTTP).

A payment sent to a plain `Tool` is ignored. It is never settled or charged.

| | MCP | HTTP (REST) |
|---|---|---|
| Payment in | `params._meta["x402/payment"]` | `PAYMENT-SIGNATURE` header (base64 JSON) |
| `PaymentRequired` out | `isError` result: `structuredContent` + the same JSON in `content[0].text` | `402`, `PAYMENT-REQUIRED` header (base64 JSON) |
| Settlement out (open) | `_meta["x402/payment-response"]` | `PAYMENT-RESPONSE` header (base64 JSON) |

There are no separate payment endpoints: payment happens on the paid tools
themselves, over whichever interface the client uses.

### How this sits with TEESwap

- **`_meta` is shared.** A result's `_meta` carries `x402/payment-response`
  next to TEESwap's SEP-2133 verifiable-tools block; a request's `params._meta`
  carries `x402/payment` next to the verifiable-tools nonce. Each is read from
  its own key.
- **Attestation.** SEP-2133 commits to `content`. On a payment-required or
  settlement-failure result, `content[0].text` carries the same `PaymentRequired`
  as `structuredContent`, as the x402 spec requires.
- **Two kinds of `isError`.** x402 results carry a `PaymentRequired` in
  `structuredContent`; TEESwap's other tool errors (no route, unknown invoice)
  are `isError` results with a plain-text message and no `structuredContent`.
- **Wire values.** `amount` and `authorization.value` are decimal strings,
  matching TEESwap's `Amount`; `maxTimeoutSeconds` is an integer.

## Facilitators

A facilitator is a third-party service that:
- Verifies payment signatures from clients
- Broadcasts transactions on-chain (pays gas)
- Returns settlement confirmation to the server

The facilitator does not hold funds. It relays signed authorizations.

TEESwap monitors multiple facilitators for liveness and capabilities. The
operator configures which facilitators to use. Defaults are provided but can
be overridden or extended.

### API surface

| Endpoint | Purpose |
|---|---|
| `GET /supported` | Returns supported schemes, networks, and extensions |
| `POST /verify` | Verify a payment payload is valid |
| `POST /settle` | Submit payment on-chain, wait for confirmation |

Liveness is judged from `/supported`, which every facilitator must serve. Some
facilitators also expose a `/health` endpoint, but it isn't part of the x402
facilitator interface and its behaviour varies, so TEESwap doesn't use it.

### Monitor cadence

Each facilitator is polled independently: `GET /supported` every
`poll_interval` seconds (default 300). A successful response marks the
facilitator healthy and refreshes its schemes, networks and extensions; any
failure marks it down until the next poll. Pollers start staggered so
facilitators aren't all hit at once.

## Payment schemes

| Scheme | Description | Use case |
|---|---|---|
| `exact` | Fixed amount transfer. Client signs authorization for exactly X. | "Pay 10 USDC for this operation" |
| `upto` | Max-cap authorization. Client authorizes up to X, facilitator settles actual amount. | "Swap roughly $1000 worth — exact amount depends on execution" |
| `batch-settlement` | Client deposits into escrow, signs off-chain vouchers per request, facilitator redeems in batches. | High-frequency micropayments |

TEESwap uses `exact` for fixed-price operations and `upto` for variable-price
swaps where the final amount depends on execution.

## Token transfer methods (EVM)

On EVM, three methods exist for moving tokens from the user to the TEE. The
method determines which tokens are supported and whether the user needs gas.

### EIP-3009: `transferWithAuthorization`

- User signs a single off-chain authorization
- Facilitator calls `transferWithAuthorization()` on the token contract
- User needs no gas — the facilitator broadcasts
- **Only works with tokens that implement EIP-3009** (USDC, EURC)
- Preferred path when available

### Permit2: `permitWitnessTransferFrom`

- User must first `approve()` the Permit2 contract for their token (one-time)
- Then user signs an off-chain Permit2 transfer authorization
- Facilitator calls Permit2's `permitWitnessTransferFrom()`
- **Works with any ERC-20** — universal fallback
- The one-time approval requires gas (see extensions below)

Permit2 contract: `0x000000000022D473030F116dDEE9F6B43aC78BA3` (same on all EVM chains)

x402 proxy contracts (CREATE2 deterministic, same on all EVM chains):
- `x402ExactPermit2Proxy`: `0x402085c248eea27d92e8b30b2c58ed07f9e20001`
- `x402UptoPermit2Proxy`: `0x4020a4f3b7b90cca423b9fabcc0ce57c6c240002`

### ERC-7710: Smart account delegation

- For smart contract accounts with delegation support
- Not yet widely adopted

## Extensions

Extensions are optional capabilities a facilitator can advertise. They affect
what tokens and flows are available.

### `eip2612GasSponsoring`

Sponsors the one-time Permit2 approval for EIP-2612 tokens.

- Token must implement EIP-2612 `permit()` (DAI, many modern ERC-20s)
- User signs a `permit()` off-chain, facilitator broadcasts it gaslessly
- After the permit, the normal Permit2 transfer flow proceeds
- User never needs gas

### `erc20ApprovalGasSponsoring`

Sponsors the one-time Permit2 approval for any ERC-20, even without EIP-2612.

- User signs a raw `approve(Permit2, amount)` transaction offline
- Facilitator sends ETH to the user's address to cover gas
- Facilitator broadcasts the user's pre-signed approval transaction
- After the approval, the normal Permit2 transfer flow proceeds
- Most expensive path — two extra transactions (gas funding + approval)
- **Works with every ERC-20**

### `bazaar`

API discovery and cataloging. Lets facilitators index what x402-protected
resources are available. Not relevant to token support — it's a discovery
protocol for building API marketplaces.

### `durable-evidence`

Records payment evidence on-chain permanently. Seen on UltravioletaDAO.

### `builder-code`

Developer tooling extension. Seen on Heurist.

## Token support matrix

The combination of transfer method + facilitator extensions determines what
tokens a facilitator can handle and whether the user needs gas:

| Token type | Method | Gas needed? | Extension required |
|---|---|---|---|
| USDC, EURC | EIP-3009 | No | None |
| EIP-2612 tokens (DAI, WETH, etc.) | Permit2 + permit | No | `eip2612GasSponsoring` |
| Any ERC-20 (incl. USDT, WBTC) | Permit2 + approve | No (sponsored) | `erc20ApprovalGasSponsoring` |
| Any ERC-20 | Permit2 + approve | Yes (user pays) | None |
| SPL tokens (Solana) | SPL Transfer | N/A | None |

## Configuration

Facilitators are part of the operator config (the `teeswap` key of the
container-init JSON). Setting `facilitators` replaces the default list.

```json
{
  "teeswap": {
    "facilitators": [
      {"url": "https://my-facilitator.example.com", "poll_interval": 300}
    ]
  }
}
```

The `teeswap x402-status <url>` CLI command tests a facilitator and prints
its status using the same code path as the monitor.
